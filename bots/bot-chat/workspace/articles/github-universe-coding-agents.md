# 让 AI 程序员在 GitHub 的海洋中学会「真正写代码」

## 一句话总结

中国人民大学、字节跳动和 AweAI 联合提出了 Scale-SWE，一套自动化的多智能体工作流，能从 GitHub 上 600 万个 Pull Request 中批量生产高质量的软件工程训练数据。最终训练出的 AI 编程助手，在行业标准测试 SWE-bench Verified 上达到了 64% 的解决率，是基础模型的近 3 倍，超越了许多参数量大得多的方案。

## 这篇论文在解决什么问题？

现在最火的 AI 应用场景之一是「AI 帮你写代码」。GitHub Copilot、Cursor 这些工具大家可能听说过。但这些工具背后的大模型，在面对复杂的真实软件工程任务时——比如修复一个涉及多个文件的 bug、理解一个几万行代码的项目结构——表现其实并不理想。

为什么？因为训练数据和真实任务之间有巨大的鸿沟。

大模型通常是在海量代码上做预训练，学会了「代码长什么样」，但这和「能在一个真实项目里定位问题、理解上下文、写出正确的修复补丁」是两回事。就好比一个人读了一万本菜谱，和他能在一个陌生厨房里用现有食材做出一顿饭，是完全不同的能力。

更要命的是，要构造这种「真实任务」的训练数据极其困难——你需要搭建可执行环境、生成测试用例、撰写问题描述，每一步都很复杂。这也是为什么现有的训练数据要么规模太小，要么质量太差，要么是合成的假数据。

这篇论文的核心问题就是：**如何大规模、自动化地从真实开源项目中构造高质量的软件工程训练数据？**

## 他们的方法：三个 AI「工人」协同作战

Scale-SWE 的核心设计是一个「沙箱化的多智能体系统」，由三个专门的 AI 智能体分工协作，把 GitHub 上的真实 Pull Request 转化为可用于训练的标准化任务实例。

### 第一个智能体：环境搭建员（EBA）

任何一个真实项目要跑起来，首先得装好依赖、配好环境。这件事对人类开发者来说都常常很头疼，何况 AI。

环境搭建员的工作是：拿到一个 GitHub 仓库，自动分析它的 setup.py、pyproject.toml、README 等配置文件，推断出需要哪些依赖，然后在 Docker 容器里一步步装好，遇到冲突就根据终端报错自动调整。最后把所有成功的安装步骤整理成一个可复现的 Dockerfile。

为了提高效率，每个仓库只对最多 10 个 PR 做完整的环境搭建，其他 PR 复用最接近的已有环境。平均下来，每个仓库可以产出 19 个有效任务实例。

### 第二个智能体：测试用例生成员（UCA）

有了环境，下一步是生成测试用例。测试用例分两类：

- **Fail-to-Pass（F2P）**：在 bug 修复前应该失败、修复后应该通过的测试，验证问题是否真的被解决了
- **Pass-to-Pass（P2P）**：原本就通过的测试，修复后也必须继续通过，确保没有引入新的问题

很多 GitHub 项目本身缺乏完善的测试，所以这个智能体需要自己写测试。它会分析 PR 的代码改动，理解修改的意图，然后在 Docker 沙箱里反复「写测试 → 运行 → 看结果 → 修改」，直到测试能准确反映问题。

### 第三个智能体：问题描述撰写员（PSWA）

最后一步是写出清晰的「问题描述」——相当于给 AI 出一道考试题。

为什么不直接用 PR 里的原始描述？因为很多 PR 描述是在修复完成后才写的，可能会泄露答案；更多的 PR 根本就没有有用的描述。

这个智能体综合 PR 的元数据和生成好的测试用例，撰写一份自包含的、不泄露解题思路的问题说明。团队发现 Google 的 Gemini3-Pro 在这项任务上表现最好，生成的描述更严谨、信息泄露更少。

## 产出了什么？

### 10 万个高质量任务实例

通过处理来自 5200 个真实仓库的 600 万个 PR，Scale-SWE 最终产出了 10 万个经过验证的任务实例——这是目前最大的此类数据集。每个实例都包含可执行的 Docker 环境、测试用例和问题描述。

一些关键数据：平均每个任务涉及 6.4 个文件的修改，中位数需要添加 43 行代码。平均每个实例有约 6 个 F2P 测试和 209 个 P2P 测试，验证非常充分。

和之前的数据集相比，Scale-SWE 在规模和多样性上都有质的飞跃。比如 SWE-Gym 只有 2400 个实例来自 11 个仓库；SWE-smith 虽有 5 万实例但都是合成的。Scale-SWE 覆盖的 bug 类型也更均衡——从 API 不匹配、逻辑错误到安全漏洞，十大类分布均匀，而合成数据集往往严重偏向某几类。

### 训练效果：从 22% 到 64%

研究团队从 2.5 万个实例中蒸馏出 7.15 万条高质量的操作轨迹（用 DeepSeek-V3.2 作为「老师」模型），然后微调了一个开源模型 Qwen3-30B-A3B-Instruct。

结果：

- 基础模型在 SWE-bench Verified 上的得分：**22%**
- 微调后（Scale-SWE-Agent）：**64%**
- 提升了近 **3 倍**

这个成绩超过了同尺寸的所有竞争对手（Qwen3-Coder 51.6%、GLM-4.7-Flash 59.2%），也超过了参数量大得多的模型（SWE-RL 用 Llama3-70B 只拿到 41%），还超过了此前最好的开源方案 KAT-Dev-32B（62.4%）。

更有意思的是对照实验：用相同的训练流程，Scale-SWE 数据训练出的模型（64.0%）显著优于 SWE-Gym（54.8%）和 SWE-smith（54.6%）。这说明大规模真实数据的价值远高于同等甚至更大规模的合成数据。

## 这项工作为什么重要？

### 1. 证明了「真实数据 > 合成数据」

在 AI 训练领域，合成数据（由 AI 自己生成的训练素材）越来越流行，因为成本低、容易扩展。但这篇论文用实验证明：对于复杂的软件工程任务，从真实世界挖掘的数据在质量上有不可替代的优势。合成数据往往偏向某些简单的 bug 类型，缺乏真实项目的复杂性和多样性。

### 2. 提出了一条完全自动化的方法论

整套流水线——从仓库筛选、环境搭建、测试生成到问题描述——全部由 AI 智能体自动完成，不需要人工标注。94% 的人工抽检通过率说明质量是有保障的。这意味着随着开源代码库的持续增长，训练数据可以持续扩展。

### 3. 小模型也能打败大模型

Scale-SWE-Agent 用的是一个 30B（激活参数只有 3B）的模型，在 SWE-bench 上打败了 70B 甚至更大的模型。这证明了：在合理的数据工程加持下，小模型的潜力远比我们想象的大。

## 局限性与未来方向

论文也坦率地讨论了局限：

- **只覆盖了 Python**：当前的流水线只处理 Python 项目。团队计划未来扩展到 Java、C、C++、Rust 等语言。
- **任务范围有限**：目前主要是 bug 修复类任务，还没有扩展到新功能开发、架构重构等更复杂的场景。
- **环境搭建成本**：每个仓库都需要能跑通的 Docker 环境，这在实际中是很大的工程挑战，尤其是在扩展到更多语言之后。

## 结语

这篇论文的核心理念很朴素：**让 AI 在真实世界中学习真实任务**。不是在合成数据上刷分，不是靠模型参数量硬堆，而是找到一种方法，自动化地从 GitHub 这个全球最大的代码协作平台上提取高质量的训练信号。

三个专业化的 AI 智能体各司其职——搭环境、写测试、出题目——组成了一条高效的数据生产线。这种「用 AI 训练 AI」的范式，不仅适用于编程领域，对于任何有丰富实践数据的领域——科学研究、数据分析、系统运维——都有借鉴价值。

当 AI 不再只是「读过」海量代码，而是真正「做过」海量编程任务时，它的能力会产生质的飞跃。
